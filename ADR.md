# Architecture Decision Records

## 1. Backend language and framework
Date: 2026-10-11
Status: Decided
Context: The app lets my boardgame obsessed friendgroup track the games we own between us and plan game nights better. 
Decision: Python 3.12 with Flask, talking to SQLite through the standard library `sqlite3` module instead of using object relational mapping (ORM). 
Alternatives considered: I considered Django, but I rejected it because its ORM, admin, auth and migration systems are far more than two small domains need and would add many files I wouldn't use. I also considered FastAPI, but I also rejected it because I would have to find a way to learn about / implement async handlers and Pydantic models which I don't currently need for this project.
Consequences: Flask allows me to have only one runtime dependency and very explicit code. The cost is that I write input validation and SQL by hand, but it's fine because it also keeps the schema visible for ADR-3.

## 2. The domains
Date: 2026-10-11
Status: Decided
Context: To bring the idea to life, the app would have to do two different jobs. The first is knowing which games the group owns and the other part would be planning nights and logging what was played. We plan nights for our friendgroup based on who is coming, how much time we have, and what we like.
Decision: I created two main packages. The first is called `library/`, which contains the games (title, owner, player range, and playtime). The second is called `group/`, which has the members of the friendgroup (members), the guests we invite (guests), nights, how much we rate each game (rating), plays, and suggestions. Group reads from Library, the first function would be "games that fit N players in M minutes" and the other is "titles of game X". A note, I decided that group stores the game ids, instead of the game details (which are in library). 
Alternatives considered: I considered putting the ratings in the library instead of in group, next to the games, but since they're unofficial ratings / opinions (and each person will have their rating separately) I thought it made more sense to keep it in group. From a software perspective, library would have to know about the members, so the two domains would depend on each other which isnt recommended. 
Consequences: Splitting library and group later instead of now means that I replace the two Python function calls I wrote above with two HTTP calls. The downside is that group only stores the games by ids instead of the names, so every time it shows a game's name it has to ask library for it, which will just be a bit slower once its a network call instead.

## 3. The database tables
Date: 2026-10-11
Status: Decided
Context: I had to design the tables for both of the domains so that each one only stores its own data. The tricky part was that group needs to refer to games (when someone rates a game or we log a play), even though games belong to library, and that friends sometimes leave the group while we still want to keep their history. 
Decision: I kept every table inside one domain. Ratings and plays have their own tables in the "Group" domain, and they store a game's ID as a plain number with no foreign key to games. Also, I decided that members who leave the group are never deleted, instead they are marked as inactive (is_active = 0) which archives them, keeps their history, and pauses their ratings. 
Alternatives considered: I considered using a foreign key from ratings and plays to games, but I rejected it because it would tie the domains together, and thinking long term, having them in the same database file would mean that it wouldn't exist anymore once they are split into separate services. I also considered deleting members when they leave, but it would delete the player history, which I'll need when I add win tracking later.
Consequences: Because there's no foreign key, a rating or a play can point at a game that doesn't exist, so group has to check with library before saving one (which is what I mentioned above). As for archived members, the consequence is that they stay in the database until someone deliberately deletes them, but on the bright side bringing someone back is as simple as setting "is_active" back to one.

## 4. Testing approach
Date: 2026-10-12 
Status: Decided
Context: In my project, the logic that I need to test the most is the night planner (the rating rules, recency points, scoring, and filling the available time), as well as the validation that stops wrong data from reaching the database. 
Decision: I tested the service functions of both of the domains with pytest against an SQLite file that each test gets in its own temporary folder. I tested the scoring functions with actual numbers. I also tested cases like archived members being rejected, what happens if seeding is done only once, and making sure that a failed night insert completely rolls back (to follow ACID principles). I also added a few route tests with Flask’s test client that check status codes, JSON errors, and one full night plan through the API.
Alternatives considered: I considered mocking the repositories so that the tests don't interact with SQLite, but I rejected it since I decided to write SQL by hand (ADR1), and the mock wouldve hidden mistakes in my queries. 
Consequences: Although the real queries catch the mistakes in my hand written sql, they remain slower than mocked tests and each one creates a database file. And when a test fails it could either be because of the logic or the query, so it takes even longer to identify the actual cause. Since I only have a handful of route tests, most error cases are only checked at the service level, so a route that passes the wrong field to the service could still slip through.

## 5. What I deliberately didn't build

Date: 2026-10-12
Status: Superseded by [8] for the UI (win tracking is still not built)
Context: The two things that are missing are a UI, which is what would actually get my friends to use the app, and tracking who wins, which we always argue about (I even kept archived members' history for it in ADR-3). But neither is needed to prove the two domains, the night planner or the container contract, and I had limited time before the deadline. 
Decision: I deliberately built the app as a JSON API only, with no frontend, and plays only records which game was played on which night as of right now without who won. I'll add a proper UI and win tracking together after the deadline. I want to take my time with it. 
Alternatives considered: I considered serving simple HTML pages with Flask templates from the same process, but I rejected it because it would've meant more routes and pages to build and test, and I'd most likely redesign them later anyway. I also considered adding a winner column to the plays table, but I rejected it because one column doesn't work for every game, like Pandemic where everyone wins or loses together, or Codenames where a whole team wins. I'd need time to think through that logic more.
Consequences: All my time went into the logic, the tests and the container, and the JSON API is exactly what a future UI (or another service in assignment 2) will call. The downside is that right now only someone comfortable with curl or a tool like Postman can use it, and nights we play before I add win tracking won't have any winners recorded. 

## 6. The split

Date: 2026-11-20
Status: Decided
Context: For Assignment 2 the monolith had to become two services, each with its own container and its own database, along the seam I described in ADR-2. The question was whether that seam would hold once the two Python calls between the domains became network calls that can either be slow or fail.
Decision: I split along the ADR-2 seam without moving it since only group calls library and its read only. Library contains the games table and group contains members, nights, night_attendees, night_guests, ratings and plays, each in its own database with its own login. Group reads GET /games/fit when planning a night, and GET /games/{id} to check a game exists before saving a rating or a play and to show titles in the reminders. ADR-2 pretty much held, as find_games_that_fit and get_game_title became those two HTTP calls through a small library_client.py with the same function names, so group's service code only changed one import. The one thing I had to add was the GET /games/{id} route, because library could list games and find the ones that fit but had no way to look up a single game. Every call has a 2 second timeout, and if library is down, too slow or answers with an error, group answers 503 with "library is unavailable, try again later" while members and nights keep working.
Alternatives considered: I considered letting the browser call both services and combine the results, but the night planner needs library's games and group's ratings and last played dates at the same time, so the scoring would have to be rewritten in JavaScript, and a check in the browser that a game exists can be skipped by calling the API directly. For library being down I considered degrading, caching and retrying. An empty night plan would look like "no games fit" when the real answer is unknown, and saving a rating without checking the game would let it point at a game that doesn't exist, so a clear failure is more honest than a guess. Caching would add data that goes stale every time someone adds a game, which isn't worth it for about seven people, and retrying inside the request would make the user wait while a sleeping library wakes up on Azure. I also considered sharing config.py and database.py between the services, but each Dockerfile can only see its own folder, so I copied them, the same way I already copied _check_positive_whole_number in Assignment 1.
Consequences: Group no longer reaches into library's repository like it did in Assignment 1. It only knows library's two endpoints, so library can change its tables freely as long as their shape stays the same. The downside is that every step across the seam is now a network call that is slower and can fail, and the database can no longer guarantee that a rating or play points at a real game. The reminders list asks library for one title per reminder, so 20 unrated plays mean 20 calls in a row. That is the "many calls" warning sign, but only titles cross the seam, so I don't think the seam is in the wrong place. For my group's handful of reminders it's fine, and if it ever gets slow, group can fetch GET /games once and look the titles up itself. The reminders could also degrade by showing the plays without titles instead of failing, which I'd change if library outages became common.

## 7. Data and migrations

Date: 2026-11-24
Status: Decided
Context: In Assignment 1 both domains shared one SQLite file and the schema was created on every boot with CREATE TABLE IF NOT EXISTS, which can add a missing table but can never change a table that already holds data. Splitting into two services meant one SQL Server database per service, and the brief requires schema changes that keep existing rows.
Decision: Each service has numbered SQL files in services/<name>/migrations and a small runner in database.py that I wrote instead of using a tool. On startup it waits for the database, creates a schema_migrations table if it is missing, and applies every file it hasn't recorded yet in number order, running each file and its record row in one transaction so a migration is either fully applied or not at all. 001_init.sql is my Assignment 1 schema ported to T-SQL, and 002_night_date_as_date.sql turns nights.night_date from YYYY-MM-DD text into a real DATE in place, which I deployed to Azure after real data was already there. No data was copied over from the SQLite file, because it only held the seed games and test entries: library re-seeds its games from seed.json when its table is empty, and group starts empty. The integrity lost at the seam is the link between ratings or plays and the game they point at, which already had no foreign key in ADR-3; group compensates by asking library (GET /games/{id}) whether the game exists before saving a rating or a play. Migrations are forward-only and applied files are never edited: a mistake gets fixed by a new migration.
Alternatives considered: I considered Alembic, but it is built around SQLAlchemy, which would add packages and an ORM layer I rejected in ADR-1, and my runner is about fifty lines I can explain completely. I also considered keeping CREATE TABLE IF NOT EXISTS on boot, but it can't change a column, so 002 would have needed dropping and recreating the table, which loses data. I didn't write down-migrations, because undoing a change that already converted data is often impossible to do safely anyway.
Consequences: Every schema change is a reviewed file in Git, and a second boot applies nothing, which the tests check. The runner is copied into both services, like the rest of database.py (ADR-6). It relies on there being only one replica (ADR-8): two containers starting at the same time could both try the same migration. My recovery plan for a bad migration in production is: if it fails, its transaction rolls back, the new container never becomes healthy and the CD health check fails, so I see it straight away and the data is untouched; if it succeeds but turns out to be wrong, I write a corrective migration, redeploy the previous image by its commit SHA if the code needs rolling back too, and if rows were damaged I restore the database from Azure SQL's automatic point-in-time backups.

## 8. Serverless hosting on Azure

Date: 2026-11-24
Status: Decided
Context: The system has to run on my own Azure for Students subscription, cost nothing while nobody uses it, and be deployed only by the pipeline after a one-time setup. The UI that ADR-5 left out is now required, as static files on an Azure Storage static website.
Decision: Everything lives in rg-jaoaljayyous-ieu2024 in francecentral. The UI is a storage account (jaoaljayyousieu2024ui) with static website hosting, billed only for storage and traffic. The two services are Container Apps on the Consumption plan in one environment, with minimum 0 and maximum 1 replica, billed per second only while they run. Azure created a Log Analytics workspace with the environment for the containers' logs, which is pay-per-use and free up to 5 GB a month. Each service has its own serverless database on one SQL server using Azure SQL's free offer, which pauses after an hour without use. The images come from GitHub Container Registry, where I made both packages public because they contain no secrets, so Azure can pull them without registry credentials. The pipeline signs in as a user-assigned managed identity with Contributor on the resource group only, through a federated credential that trusts runs on main of my repository, so no Azure password exists anywhere.
Alternatives considered: I considered Azure Container Registry, but it has a fixed monthly cost, while public GHCR packages are free. I considered keeping one replica always running to avoid cold starts, which ADR-10 explains. A provisioned database would never pause, but it costs money every month even when nobody plays.
Consequences: Nothing has a fixed monthly cost, but scale-to-zero means the first request after a quiet period finds the container stopped and often the database paused too. Resuming the database takes up to about a minute, so wait_for_database retries with growing pauses (2, 4, 8, 16 and then 30 seconds), Azure answers that first request with a 503 after about 30 seconds, the UI shows a "starting up, try again" message instead of a blank page, and the CD health check retries for a few minutes. Migrations run at startup, which is only safe because there is never more than one replica, and the CD workflow only allows one deploy at a time. At 100x the traffic I would raise the maximum replicas, which means moving migrations out of startup into a separate step of the pipeline, keep at least one replica warm, move the databases off the free offer to a bigger serverless size, and stop the reminders list from calling library once per reminder (ADR-6).

## 9. Pipeline and testing

Date: 2026-11-24
Status: Decided
Context: Every push has to be linted, tested and built, and every merge to main deployed with no manual steps. My tests talk to a real database (ADR-4), so CI needs SQL Server, and the brief asks for at least one test across the seam.
Decision: CI runs on every push to a branch and every pull request, once per service: ruff, then pytest against a real SQL Server that CI starts from the same docker-compose file I use locally, with the example passwords from .env.example, then a coverage gate that fails below 70% on the service's own package plus database.py (library 88.7%, group 90.3% when I added it), and finally a Docker build of both images. On main, the CD workflow runs that same CI file first, which also pushes both images to GHCR tagged with the commit SHA, then deploys those exact images to Azure, uploads the UI with the Azure addresses in config.js and fails the run if either /health doesn't return 200 within a few minutes. The cross-seam tests replace library with a stub: group's tests swap library_client's two functions for a pretend library, including one that raises the same error the real client raises when library is down and checks that the plan request answers 503 with the clear message.
Alternatives considered: I considered running the cross-seam test against the full compose stack with both services, but then every group test run would depend on library's container and seed data, so a library bug could fail group's tests and the failures would be harder to read. The stub keeps group's tests fast and only about group's own logic. I also considered mocking the database in CI to avoid starting SQL Server, but I rejected that for the same reason as ADR-4.
Consequences: A commit can only reach Azure if lint, tests, coverage and both image builds passed. The stub can't catch a mismatch between what library really answers and what the pretend library returns, so the real HTTP path in library_client.py (timeouts, status codes) is only checked by hand with docker compose stop library, which is why that file has the lowest coverage. I deliberately don't test the UI's JavaScript, the Azure deploy itself beyond the health check, or the retry loop that only runs while the database is down. The tests share each service's local database and empty its tables first, so running them wipes whatever I created by hand locally, while CI always starts from a fresh database.

## 10. What I deliberately didn't build (keeping the services always on)

Date: 2026-11-21
Status: Decided
Context: On Azure, both services switch off when nobody has used them for a few minutes, and the databases switch off after an hour, so the app costs almost nothing while no one is using it. My friendgroup opens the planner about once a week, on game night, so almost every time, everything will be switched off and the first person will wait up to about a minute while it turns back on.
Decision: I let everything switch off when it isn't used. While the services are starting up, the page shows a "starting up, try again in a moment" message instead of a blank page.
Alternatives considered: I considered keeping one copy of the group service always running, since it's the one the page calls first, so nobody would ever wait. I rejected it because the assignment doesn't allow anything that runs and costs money while nobody is using the app, and Azure would charge for every second it runs, mostly while no one is using it, just to avoid a one-minute wait once a week (not worth it). Keeping the database always on as well would mean a paid database plan instead of the free one.
Consequences: The app costs almost nothing, but the first visit of every game night is only slightly slower and the page has to handle that first failed request clearly. It would be worth keeping group always on if my friends started using the planner every day, or if the wait put them off opening it.
